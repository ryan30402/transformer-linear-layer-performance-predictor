2. What the numbers measure

The target is Y[M,N] = X[M,K] @ W[N,K].T, measured using preallocated torch.mm(..., out=Y) inside repeated CUDA graphs. Each recorded event interval is divided by the actual captured GEMM count. A visit uses the median of nine such samples; a final label uses the median of three visits.

The quantity includes GPU execution and gaps visible within the graph-replay event interval. GPU reads and writes of the resident tensors contribute to it. Allocation, CPU–GPU transfer, reference checks, warmup, profiling, fitting, model loading, and network/server time are outside this target. It is not a pure kernel-only duration or end-to-end Transformer latency.

Warm reuse repeatedly uses the same buffers. Rotating buffers alternates four sets for eligible shapes. Rotation does not guarantee a cold cache or measured HBM traffic. The recorded 40 MiB L2 size gives an 80 MiB weight-matrix eligibility threshold; 180 primary and 28 repeat precision/cache variants were deliberately ineligible, all for weight_exceeds_declared_L2_multiple. Their warm measurements are retained. No memory-guard skips appear in these files.

The hardware context is NVIDIA A100-SXM4-40GB, 108 SMs, with the same recorded UUID and matching software contexts for primary and repeat. Software: Python 3.13.16, PyTorch 2.11.0+cu130, CUDA runtime 13.0, driver 580.82.07. Matching context does not establish locked clocks, identical thermal state, or isolated background activity.

4. Selection discipline and comparators

The workflow collects every split before fitting. Selection then uses only training labels in six cross-validation folds grouped by N/K family, with feature standardization fitted within each fold. Each context evaluates 19 configurations across five model families. The chosen configuration is refitted on all eligible training rows (266 for rotating, 311 for warm reuse). Test, challenge, stress, and repeat labels are absent from training/selection; profiling data are excluded from features.

This implements an offline dataset workflow with isolated evaluation labels. It does not require holding off measurement of held-out cases until after model freezing.

7. Concrete model limitations

A. A correction bound limits small-matrix predictions

The selected KRR corrects a zero-overhead two-parameter roofline baseline by a multiplier clipped to the range 0.25–4. This upper bound is active on 7–10 ordinary-test cases per context. The worst ordinary-test rows are in the narrow N=128, K=896 family, and their timing-quality checks pass.

This demonstrates an active structural restriction. It does not prove that removing the bound is the best general solution. A future revision should compare an additive-overhead baseline and training-CV-selected correction bounds, including failure behavior outside the training region.

B. Irregular dimensions are outside training support

All training values for the four N/K alignment indicators are zero. Stress switches those dimensions to irregular values. The model has no training examples from which to learn the observed irregular-dimension slowdown. Stress predictions are systematically low, and no stress correction is actively clipped; relaxing the small-matrix correction bound alone does not address this failure.

A future data design needs representative irregular training/development examples while retaining new, unexposed evaluation families. The current irregular stress result is useful evidence of the boundary of this model.

C. Warm unseen-family predictions remain weak

Warm challenge has about 29% weighted mean error, including cases with large overprediction. Restricting both cache contexts to the same 100 challenge shapes still gives about 29% warm error, so the difference is not simply the 18 additional warm-only cases. However, target latencies and fitted models differ between contexts; this is not a controlled attribution of error to cache behavior. The worst challenge cases are not the six flagged-quality rows.

8. Arithmetic, profiling, and backup evidence

Every stored arithmetic-check record satisfies its declared finite, relative-L2, and maximum-absolute-error conditions. Across primary measurements, controls, and profiles, maximum relative-L2 error is 0.023977% for FP16 (limit 0.2%) and 0.186757% for BF16 (limit 1%). These are matrix arithmetic errors, not latency-prediction errors.

The reference is FP32 IEEE-mode torch.mm on the same already-represented low-precision inputs. It is not a float64 oracle. The maximum-absolute check uses atol + rtol × max_abs(reference), rather than elementwise allclose. Output/reference matrices are not archived, so this offline review can verify record consistency and coverage but cannot independently recompute the matrix products.

All 1,372 separate traces contain CUDA kernel events. In 231 primary and 23 repeat captures, one GEMM involves two kernels, including reduction paths. Dividing graph time by GEMM count, rather than kernel-event count, preserves the intended target. All profiling is warm reuse after timing; rotating-buffer variants do not have their own profiling captures. Profiler outputs are excluded from model inputs and labels.

Hardware counters were not collected. The available traces do not establish Tensor Core utilization, measured occupancy, HBM traffic, cache hit rate, or causal stall explanations.

There are 15 verified checkpoint receipts, totaling 30.458 seconds, with no failed receipt. Their timestamps overlap none of the 8,058 raw-visit/control measurement envelopes. This supports exclusion of backup-copy time from those measurement intervals, while leaving indirect state effects unproven. The final complete ZIP's Drive-copy result is reported outside the ZIP, so this review does not independently confirm that final file's current remote presence.

9. What to do with this run

Keep this completed experiment as the baseline evidence. The timing-quality findings alone do not justify discarding it or immediately rerunning the entire workload. Keep the quality qualifications, baselines, and full error distributions attached to its results.

  1. Prioritize model coverage. Evaluate an overhead-aware predictor, the correction-bound design, and irregular-dimension training coverage. These address observed prediction failures; a more expensive GPU does not by itself repair them.
  2. If more measurement is needed, make it diagnostic. Target the four geometric shapes represented by the six flagged rows, the warm 28% repeat outlier, and startup control behavior. Preserve this run and label the new records as follow-up measurements.
  3. Maintain ordinary evaluation discipline. This test set has now informed diagnosis. Use it for regression analysis while reserving new cases for final assessment of a revised model. New labels may still be collected together before fitting; training, selection, and final evaluation must remain isolated.
  4. Bound the public claim. State the A100, precision, cache policy, preallocated graph target, weighted error, split definitions, quality flags, and stress limitations. Do not turn these results into a claim about full LLM serving, arbitrary GPUs, or universal low error.

On an A100-SXM4-40GB under the declared preallocated CUDA-graph GEMM workload, the training-CV-selected predictor achieved 7.71%–10.32% weighted mean absolute percentage error on ordinary held-out shapes. Warm-reuse unseen-family error was about 29%, and irregular stress error was 49.47%–57.31%. Typical same-session repeat changes were about 1%–2%, with retained quality flags and larger tail discrepancies.
